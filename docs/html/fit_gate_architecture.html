The fit gate: separating sequencing from packing

A tried architecture for the concurrent-packing task (jobs claim a random fraction of a machine's capacity instead of always claiming all of it, so multiple jobs can run on one machine at once). Job/machine attention reasons only about identity and timing; a second, structurally separate path reasons about capacity fit, and a learned gate decides how much the second path should move the final score. Result: a clear regression — see "Progression against SJF" below. The current best on this task remains the simpler design one step before this one (direct concatenation, no gate).

Two paths that never mix until the very last step

Everything in the amber/blue attention path is capacity-blind — it never sees usage or free capacity, only job identity (status, size, wait_time, ttl) and machine load history. Separately, the feature extractor emits raw, unembedded usage and free_capacity_now straight through, with no MLP or attention touching them. The two paths meet only at the very end, at the actor's scorer.

Why this didn't work

Steps 1-3 all worked by concatenating capacity information into whatever the network was already computing — first into the job embedding itself, then into score_net's input — and each time the network had to use that information at whatever weight training converged on, uniformly across every situation. The hypothesis behind this design was that fully separating the two paths and gating their combination would repeat the pattern that fixed an earlier regression in this project: the ungated dual cross-attention (log #15) made the policy more decisive without being more accurate, and a LayerScale-style zero-initialized gate fixed it by letting training decide how much of the new signal to trust.

That pattern didn't transfer here. The most likely difference: log #15's gate scaled a cross-attention output being added back into an embedding that was already receiving a useful gradient from everywhere else in the network. Here, score_net and fit_gate_net are two separate heads that both had to be learned from scratch, sharing the same embedding input but producing two different quantities (a score and a gate) that only combine multiplicatively at the very end. That's a harder credit-assignment problem than one network learning [embeddings, fit] → score directly (step 3's design) — the gate has to learn when to trust a signal at the same time the embeddings feeding it are themselves still being learned, and 2M steps wasn't enough for that joint optimization to converge to something useful. Reverted; step 3 (direct concatenation, no gate) remains the current best on this task.
